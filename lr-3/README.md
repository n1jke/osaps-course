Лабораторная работа №3
Взаимодействие процессов: обмен данными
1. Цель работы
Изучить механизмы межпроцессного взаимодействия (IPC – Inter-Process Communication) в операционной системе Windows и получить практические навыки организации обмена данными между независимыми процессами.

В ходе выполнения лабораторной работы необходимо освоить:

- создание нескольких взаимодействующих процессов;
- передачу данных между процессами;
- разработку собственного простого протокола обмена сообщениями;
- использование каналов (Pipe);
- использование именованных каналов (Named Pipe);
- использование разделяемой памяти;
- применение объектов синхронизации при работе с разделяемой памятью;
- использование Mailslot;
- согласование работы процессов;
- обработку отключения или аварийного завершения одного из участников;
- предотвращение повреждения совместно используемых данных;
- измерение характеристик IPC;
- корректное освобождение системных ресурсов.

2. Теоретическая часть
Перед выполнением лабораторной работы необходимо изучить следующие вопросы.

2.1. Изоляция процессов
Каждый процесс Windows имеет собственное виртуальное адресное пространство.

Один процесс не может непосредственно обращаться к обычным переменным другого процесса.

Для обмена информацией между процессами используются специальные механизмы IPC.

Необходимо понимать различие между:

- передачей копии данных другому процессу;
- совместным использованием одной области данных;
- обменом сообщениями;
- синхронизацией доступа к общему ресурсу.

2.2. Неименованные каналы
Неименованный канал (Anonymous Pipe) используется преимущественно для взаимодействия связанных процессов, например родительского и дочернего.

Основные функции Windows API:

CreatePipe()
ReadFile()
WriteFile()
SetHandleInformation()
CloseHandle()

Необходимо понимать механизм наследования дескрипторов дочерним процессом.

2.3. Именованные каналы
Named Pipe позволяет организовать обмен между независимыми процессами.

Основные функции:

CreateNamedPipe()
ConnectNamedPipe()
CreateFile()
ReadFile()
WriteFile()
DisconnectNamedPipe()
CloseHandle()

Необходимо знать различие между:

- односторонним;
- двусторонним обменом;
- byte mode;
- message mode.

2.4. Разделяемая память
В Windows разделяемая память может быть реализована посредством объекта отображения файла.

Основные функции:

CreateFileMapping()
OpenFileMapping()
MapViewOfFile()
UnmapViewOfFile()

При использовании разделяемой памяти несколько процессов могут одновременно получить доступ к одним данным.

Следовательно, возникает задача синхронизации.

2.5. Синхронизация процессов
Для согласования работы процессов могут использоваться:

CreateMutex()
OpenMutex()
ReleaseMutex()

CreateSemaphore()
OpenSemaphore()
ReleaseSemaphore()

CreateEvent()
OpenEvent()
SetEvent()
ResetEvent()

WaitForSingleObject()
WaitForMultipleObjects()

Необходимо понимать назначение:

- Mutex;
- Semaphore;
- Event.

2.6. Mailslot
Mailslot представляет собой механизм односторонней передачи сообщений.

Основные функции:

CreateMailslot()
CreateFile()
ReadFile()
WriteFile()

Следует учитывать, что Mailslot имеет иные свойства надежности и организации обмена, чем Named Pipe.

3. Общая постановка задачи
Разработать программный комплекс из двух или более отдельных процессов, которые взаимодействуют посредством заданного в индивидуальном варианте механизма IPC.

Использование глобальных переменных одного процесса в качестве механизма обмена между участниками не допускается.

Приложения могут быть консольными.

Основная сложность лабораторной работы должна заключаться не в вычислительном алгоритме, а в правильной организации:

процесс → IPC → протокол → обработка → IPC → результат.

4. Обязательные требования для всех вариантов

4.1. Участники взаимодействия
В программе должно участвовать не менее двух процессов.

Если вариант предусматривает модель «сервер – клиенты» или «диспетчер – рабочие», необходимо обеспечить работу минимум:

- одного управляющего процесса;
- трех одновременно работающих клиентских или рабочих процессов.

4.2. Идентификация процессов
При запуске каждый процесс должен выводить:

- свою роль;
- PID;
- номер варианта;
- идентификатор текущего запуска RUN_ID.

Пример:

WORKER #2 | PID=7452 | VARIANT=7 | RUN_ID=381

Параметр RUN_ID передается программе через командную строку.

Он должен присутствовать в журнале всех основных операций обмена.

5. Формат сообщения
Для вариантов, использующих передачу сообщений, необходимо самостоятельно определить формат сообщения.

Каждое сообщение должно содержать как минимум:

version
messageType
sourcePid
requestId
payloadSize
payload

Например:

struct MessageHeader
{
    uint32_t version;
    uint32_t messageType;
    uint32_t sourcePid;
    uint32_t requestId;
    uint32_t payloadSize;
};

Студент может изменить структуру, если это необходимо для его варианта.

Запрещается передавать структуры, содержащие обычные указатели, предполагая, что указатель будет корректно работать в другом процессе.

6. Журнал взаимодействия
Каждый процесс должен выводить основные события.

Минимальный формат:

[12:43:05.125] PID=5312 SEND requestId=17 type=TASK size=1024

и:

[12:43:05.143] PID=8124 RECEIVE requestId=17 type=TASK size=1024

По журналу должно быть возможно восстановить последовательность взаимодействия процессов.

7. Обработка ошибок
Программа должна корректно обрабатывать как минимум:

- невозможность создания IPC-объекта;
- невозможность подключения;
- ошибку чтения;
- ошибку записи;
- закрытие канала другим процессом;
- некорректный размер сообщения;
- неизвестный тип сообщения;
- аварийное завершение одного из участников.

Для ошибок Windows API необходимо выводить:

- функцию, завершившуюся с ошибкой;
- GetLastError();
- текст ошибки.
8. Завершение работы
Необходимо предусмотреть корректное завершение комплекса.

Запрещается считать нормальным способом завершения постоянное использование TerminateProcess().

Для штатного завершения должен существовать соответствующий элемент протокола, например:

STOP

или:

SHUTDOWN.

Все созданные:

- HANDLE;
- Pipe;
- Mapping;
- Event;
- Mutex;
- Semaphore

должны корректно освобождаться.

9. Проверка производительности
Для своего механизма IPC студент должен выполнить небольшой эксперимент.

Передать последовательно не менее 1000 сообщений и измерить:

- общее время обмена;
- количество сообщений в секунду.

В зависимости от варианта использовать сообщения двух размеров:

- небольшое – приблизительно 64 байта;
- крупное – не менее 4 КБ.

Результаты привести в отчете.

Цель данного эксперимента – не сравнение результатов студентов между собой, а исследование поведения собственной реализации.

10. Правила использования моделей искусственного интеллекта
Использование моделей ИИ полностью не запрещается.

Допускается применять ИИ для:

- объяснения Windows API;
- поиска причин ошибки;
- объяснения документации;
- проверки отдельного фрагмента программы;
- поиска возможных ошибок;
- получения справочной информации.

Однако студент несет полную ответственность за предоставленный программный код.

На защите считается, что любая строка представленного исходного кода написана или проверена самим студентом и понятна ему.

Если ИИ использовался при разработке, в конце отчета необходимо добавить небольшой раздел:

Использование ИИ

Указать:

- какой инструмент использовался;
- для какой задачи;
- какой результат был получен;
- что студент изменил или проверил самостоятельно.

Например:

Использовался ChatGPT для объяснения поведения

ConnectNamedPipe() при подключении клиента до вызова функции.

Полученное объяснение было проверено экспериментально.

Архитектура программы и протокол обмена разработаны самостоятельно.

Сам факт использования ИИ не снижает оценку.

Оценка снижается за неспособность объяснить или изменить представленную программу.

11. Проверка самостоятельности выполнения
При защите преподаватель задает студенту одно небольшое изменение программы.

Например:

- добавить новое поле сообщения;
- изменить количество рабочих процессов;
- добавить новый тип сообщения;
- изменить размер общего буфера;
- изменить тайм-аут;
- изменить условие маршрутизации;
- добавить нового клиента;
- вывести дополнительное поле в журнал;
- обработать отключение определенного процесса;
- изменить порядок обработки.

Изменение выполняется на существующей программе студента.

Также преподаватель может попросить студента объяснить:

- назначение конкретной структуры;
- назначение конкретного HANDLE;
- жизненный цикл сообщения;
- какую функцию Windows API вызывает конкретный участок;
- что произойдет при завершении одного из процессов;
- почему используется именно данный объект синхронизации.

12. Индивидуализация работы
Чтобы результаты студентов отличались не только номером варианта, каждый студент использует:

VARIANT_ID = номер варианта

STUDENT_ID = индивидуальное число, последние 3 цифры студенческого

STUDENT_ID необходимо использовать минимум в двух параметрах программы.

Например:

количество заданий = 500 + STUDENT_ID * 10

или:

начальное значение генератора = STUDENT_ID

или:

размер сообщения = 1024 + STUDENT_ID

Конкретные формулы студент указывает в отчете.

13. Обязательная демонстрация ошибок
На защите студент должен показать не только нормальную работу программы, но и минимум один аварийный сценарий.

Например:

1. завершить Worker во время обработки;
2. завершить Client;
3. запустить Client без Server;
4. отправить сообщение неизвестного типа;
5. передать некорректный размер сообщения.

Программа не должна аварийно завершать остальные процессы без объяснимой причины.
