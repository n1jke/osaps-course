# RFC: ЛР №3, вариант 26 — логирование через Mailslot

Статус: решение согласовано, реализация подготовлена.

## Цель и границы

Три независимых клиента передают логи одному серверу через локальный Mailslot. Сервер проверяет сообщения и сохраняет их в текстовый файл: один LOG — одна строка.

В MVP входят протокол, завершение, ручные проверки и измерения. Сетевой обмен, подтверждения доставки, повторная отправка и восстановление сервера не входят. Mailslot сравнивается с Named Pipe только теоретически.

## Интерфейс и ход работы

Один исполняемый файл, четыре отдельных процесса, ручной запуск в разных терминалах:

```text
lr3 server --run-id N --log PATH [--timeout-ms T]
lr3 client --run-id N --client-id K [--size B]
```

Сначала сервер создаёт `\\.\mailslot\lr3_<RUN_ID>` и выводит READY, затем запускаются клиенты 1..3. Все используют один RUN_ID. Каждый процесс выводит роль, PID, VARIANT, STUDENT_ID и RUN_ID.

В `config.h`: VARIANT_ID=26, STUDENT_ID=112. Каждый клиент отправляет `1000 + STUDENT_ID = 1112` логов; начальное значение генератора — `STUDENT_ID + clientId` (113, 114, 115). За успешный запуск сервер получает 3336 LOG и три DONE.

Клиент открывает канал, последовательно отправляет LOG, затем DONE и закрывает дескриптор. Сервер ведёт состояние каждого клиента, после трёх DONE проверяет полноту и завершает работу. Общий порядок сообщений разных клиентов не задаётся.

RUN_ID — положительный uint32_t; clientId — 1..3; полный размер LOG — 37..4096 байт, по умолчанию 64. Неверные, повторные и неприменимые к роли аргументы отклоняются до создания ресурсов.

Коды завершения: 0 — успех, 1 — ошибка выполнения/протокола или неполный обмен, 2 — ошибка аргументов. Успех клиента означает отправку, а не подтверждённую запись сервером.

## Формат и проверка сообщений

Бинарная сериализация явная, little-endian, без указателей и padding C++-структур. Заголовок — 36 байт:

| Смещение | Поле | Тип |
|---|---|---|
| 0 | version | uint32_t |
| 4 | messageType | uint32_t |
| 8 | sourcePid | uint32_t |
| 12 | requestId | uint32_t |
| 16 | payloadSize | uint32_t |
| 20 | runId | uint32_t |
| 24 | clientId | uint32_t |
| 28 | send_at | uint64_t, Unix-миллисекунды |

- LOG=1: requestId от 1 до 1112, payload — непустой ASCII-текст. При размерах 64 и 4096 байт текст занимает 28 и 4060 байт.
- DONE=2: requestId=0, payload — число отправленных логов как uint32_t; полный размер — 40 байт.

Сервер проверяет фактическую длину, payloadSize, версию, тип, RUN_ID, clientId, PID и последовательность. Первый корректный пакет связывает номер клиента с PID. Повреждённые пакеты и дубликаты пропускаются с диагностикой, запуск помечается ошибочным. DONE учитывается один раз на клиента. После трёх DONE приём прекращается; до этого сообщения от завершившихся клиентов отклоняются.

## IPC, журнал и ресурсы

Сервер создаёт канал через CreateMailslotA с пределом 4096 байт. Клиент открывает его через CreateFileA с GENERIC_WRITE, FILE_SHARE_READ, OPEN_EXISTING и пишет одним WriteFile на сообщение. Частичная запись сообщения — ошибка; остаток отдельным пакетом не отправляется.

Серверный дескриптор [асинхронный](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createmailslota). Чтение использует GetMailslotInfo, ReadFile, OVERLAPPED с одним неназванным событием и GetOverlappedResult. SetMailslotInfo задаёт оставшееся время ожидания. Буфер и OVERLAPPED живут до завершения операции; одновременно выполняется одно чтение.

Журнал создаётся через CreateFileA с GENERIC_WRITE, нулевым режимом совместного доступа и CREATE_NEW: существующий файл вызывает ошибку. Строка содержит время приёма, RUN_ID, PID отправителя, clientId, requestId, время отправки, длину и текст. Разделители, обратные косые черты и управляющие символы экранируются. Частичные записи файла дописываются циклом. DONE и ошибки остаются в консоли.

События SEND/RECEIVE содержат время, PID, RUN_ID, тип, requestId и размер. Ошибки WinAPI содержат имя функции, немедленно сохранённый GetLastError и описание FormatMessageA. Ошибка создания, чтения или записи завершает соответствующий процесс. При отсутствии валидного прогресса сервер завершает ожидание по тайм-ауту и показывает неполных клиентов; повреждённые сообщения и дубликаты ожидание не продлевают.

HANDLE принадлежат unique_ptr с CloseHandle и закрываются при исключении. Память FormatMessageA освобождается через LocalFree. Штатного TerminateProcess нет. Успех сервера требует всех LOG, трёх корректных DONE, отсутствия ошибок протокола и успешного закрытия журнала. Принудительный сброс на физический носитель не выполняется.

## Структура и проверки

- main.cpp — роли, координация, состояние клиентов, журнал и измерения.
- cli.h/.cpp — аргументы и справка.
- protocol.h/.cpp — сериализация, разбор и экранирование.
- mailslot.h/.cpp — WinAPI и диагностика.
- config.h — индивидуальные константы.
